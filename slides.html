The Question
We experience different "feelings" in different places.

But how different are they, really?
Outside near a pond. Inside near running servers. These places feel different — but no one's measured the actual difference with real data.
Hypothesis
If...
a DHT11 sensor is placed in three different microenvironments for 5 minutes each...
Then...
the readings will show that areas near water have higher humidity, and areas near electronics have higher temperature, compared to a neutral indoor location.

Because water evaporates into the surrounding air, increasing humidity near the pond, and electronics convert electrical energy into waste heat, raising local temperature.

Research Question
How do temperature and humidity readings vary across three different microenvironments — outdoor near water, indoor near electronics, and a neutral indoor location — over equal 5-minute sampling periods?

The Code
sensor_logger.py 
import board, time, csv
from datetime import datetime
import adafruit_dht

# Initialize DHT11 sensor on GPIO pin D4
sensor = adafruit_dht.DHT11(board.D4)

LOCATION = "pond_edge"
DURATION = 300  # 5 minutes in seconds
INTERVAL = 10   # reading every 10s

with open(f"data_{LOCATION}.csv", "w") as f:
    writer = csv.writer(f)
    writer.writerow(["timestamp", "temp_C", "humidity_%"])
    
    start = time.time()
    while time.time() - start < DURATION:
        writer.writerow([
            datetime.now().isoformat(),
            round(sensor.temperature, 1),
            round(sensor.humidity, 1)
        ])
        time.sleep(INTERVAL)
    
    print(✅ Data collection complete)

Limitations & Sources of Error
Sensor Accuracy
DHT11 has ±2°C and ±5% RH margin of error. Real readings could shift by this much in either direction.
Short Sampling
Only 5 minutes per location. A longer window would catch fluctuations — like servers ramping up or wind shifting.
Single Time Point
All tests done in one 20-minute window. Time of day, sunlight, and weather all affect microclimates.
What I'd Do Differently
Longer sampling (30+ min), multiple days, more locations, and a backup sensor to cross-check readings.
Being honest about limitations is part of science — it shows you understand the method, not just the result.
Why It Matters
Microclimates affect comfort, energy use,
and even hardware lifespan.
Server rooms that overheat cost companies millions in cooling. A 9.5°C swing between two rooms in the same building shows why sensor placement matters. Even a 2°C difference affects hardware failure rates.

Greenhouses need 60-80% humidity for most crops — our pond edge hit 82%. Homes need 30-50% for comfort and to prevent mold — our hallway sat at 47%.

Understanding microclimates with real data helps us make better decisions about where to put things — from plants to computers to people.
Define the Problem
Q1 — What problem are we solving?
Making it easier for people to monitor temperature and humidity at home — in real time, from anywhere — without buying expensive equipment.
Q2 — Who is impacted most?
People who want instant temperature and humidity information for a specific place — like homeowners with server rooms, people with plants that need certain conditions, or anyone who just wants to know what the air is actually like around them.
Q3 — What options exist today?
Temperature controllers that also monitor humidity — but they are expensive, they only work in one fixed location, and most of them do not let you check the data remotely.

Q9 — Who might be missing?

Imagine Possibilities
Q21 — What do people need most?
A simple, low-cost device that reads temperature and humidity and shows the data somewhere they can check it — like a small screen or a phone. Nothing complicated. Just the numbers, updated in real time.
Q22 — What solution are we moving forward with?
A Raspberry Pi with a BME280 sensor, running a Python script that logs data to a CSV file. The Pi displays the readings on a small LED matrix — the Unicorn HAT Mini — so you can see the numbers at a glance. Same pattern as commercial monitors, but instead of paying $200, it costs under $50 and you build it yourself.
Build a Prototype
Q23 — Step-by-step plan
1. Connect the BME280 sensor to the Raspberry Pi GPIO pins using jumper wires and a breadboard.
2. Install the sensor library and write the Python logging script.
3. Test the script at home — make sure it reads correctly and saves to CSV.
4. Set up the Unicorn HAT Mini to display live readings.
5. Take the device to each of the three locations and run the script for 5 minutes.
6. Collect the CSV files and compare the data.
Q24 — Materials needed
Raspberry Pi 5, BME280 sensor, breadboard, jumper wires, power bank, laptop for SSH, Unicorn HAT Mini for display.
Q25 — Anticipated problems
Sensor connection issues — loose wires are the most common problem. Power running out during outdoor testing. Script crashing if the sensor disconnects. Fix: secure all connections, bring a backup power bank, and add error handling to the code.
Share, Test & Improve

Adding a visible timestamp on the display so anyone watching knows when the last reading was taken. Also making the code more robust — if the sensor disconnects, it retries instead of crashing.
Q28 — Test description
Place the sensor in three different microenvironments — pond edge, homelab, and hallway — for five minutes each. The script records temperature and humidity every ten seconds. After all three locations are tested, compare the CSV data to see how the readings differ.
Success Criteria & Data Analysis
Q31 — Success criteria
The test is successful if: (1) all three locations produce 30 readings each with no gaps, (2) the pond edge shows higher humidity than the hallway, and (3) the homelab shows higher temperature than the hallway. If the data matches the hypothesis, the experiment worked.
Q32 — Analyze data
Calculate the average temperature and humidity for each location. Compare the three averages. Check if the numbers follow the predicted pattern — pond = humid, homelab = hot, hallway = in the middle.
Q33 — Graphical representation
A grouped bar chart — one group per location, with two bars each (temperature and humidity). This makes it easy to compare all three locations side by side.
Results & Improvements
Q34 — What was successful?
The sensor read consistently across all three locations. The CSV files were clean and complete — 30 readings each, no gaps. The Python script ran without errors at every location.
Q35 — What was unsuccessful?
The DHT11 sensor originally planned broke during setup — could not get it soldered properly. Had to switch to the BME280 and use a weather API for the display temperature. The outdoor reading near the pond was also affected by wind, which made the numbers jump around more than expected.
Q36 — Improvements based on tests
Use a wind shield for outdoor readings to stop the numbers from jumping. Add error handling in the code so a loose wire does not crash the whole script. Add a small screen or LED display so you can see the readings without needing a laptop. And test more than three locations to get a bigger picture of how microclimates work.
